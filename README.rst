Read-only Bejerman seller, customer, and debt source for Collections.

Adds connector type ``bejerman``. Each ERP read opens a SOAP session
over a vendored httpx client: Registro, then Ejecutar, then Cierre even
when Ejecutar fails. Reads need TABLAS ``ObtenerClientes`` plus the
query views of the connector's profile; missing grants fail closed.
There is no receipt write-back, no MCP, no sample ERP data, and no
``post_init_hook``; its only menu is the **Bejerman Debt** list. Depends
on ``collection`` and ``mail``. Requires the ``httpx`` Python extra.
Credentials and connection settings use the shared connector form opened
by **Configure Connection**. Credentials, endpoint, TLS, server paths
and the session deadline are Settings-only (``base.group_system``);
clave is password-masked. Collections Managers can edit company,
workstation, branch and timeout for their company. Test Connection needs
an administrator or a Collections Manager of the connector's company.
Transient failures are retried up to 3 times with exponential backoff
and jitter (an HTTP ``Retry-After`` is honoured, capped at 30 s): the
read operations on connect errors, timeouts, dropped connections, HTTP
429 and 5xx; Registro only when the server cannot have processed it
(connect errors, HTTP 429 and 503), so a lost answer never opens a
second ERP session; CierreProceso never. One session (login, reads,
retries and close) must finish within **Bejerman Deadline (s)** (default
900): each request's timeout is capped by the time left and every answer
is read in chunks against it, so a slowly trickling download is aborted.
The HTTP client is closed on every path, a failed login included. Faults
raise a generic ``UserError`` with no SOAP, Token, URL, user, or clave.
Customer listing and customer debt are seller-scoped and stay in this
addon; ``collection`` does not call Bejerman.

Profiles: several customers' connectors share one database, and each
customer's ERP has its own query views. **Bejerman Profile** picks, per
connector, the addon that reads the debt; a customer addon adds its
value (``collection_connector_bejerman_kras`` adds ``kras``) and acts
only on the connectors of that profile. The ``standard`` profile reads
customers only and has no debt source: its refresh fails closed with a
configuration error before any request, so the cron records it and tells
the managers, and no debt is ever served as zero. A profile overrides
``_bejerman_check_snapshot_source`` (its own settings, checked before
the session opens) and ``_bejerman_read_snapshot`` (customers, open debt
and sellers read inside the open session); it may extend
``_bejerman_invoice_payload``. A debt row without ``amount_untaxed``
makes ``collection`` pay the commission on the total.

Debt snapshot: debt views are large downloads, so they are never read
per question. A refresh reads, in one session, what the profile reads,
and replaces the stored snapshot in one transaction
(``collection.connector.bejerman.debt``,
``collection.connector.bejerman.customer``, with each customer's open
credit, and ``collection.connector.bejerman.seller``). A failed refresh
keeps the previous snapshot. The snapshot rows are read-only and visible
only to Collections Users (operators and the MCP API user) of the
company; plain internal users cannot read them, and administrators keep
full access. Refresh runs every 4 hours (``ir.cron``) and from **Refresh
Debt** for administrators and the connector company's Collections
Managers. Before the first refresh, ``list_customers`` and
``get_customer_debt`` fail closed with the generic "not configured"
error rather than downloading inline.

Sync status: the connector form's **Debt Sync** tab (collections
managers and administrators) shows when the last successful refresh
started and ended, the row counts (including the rows skipped because
their balance or amount could not be read: they are logged as a count,
never stored as 0), and the last scheduled failure with a generic reason
class (connection, timeout, ERP refusal, configuration, unreadable
answer, storage) and the number of failures since the last success. Only
a refresh writes these fields. When the cron fails, every collections
manager of the connector's company gets one **Bejerman sync failed**
activity on the connector; further failures add none, and the next
successful refresh removes it. The cron itself does not fail, so it is
never deactivated. A failing manual **Refresh Debt** shows its error to
the operator instead. Debt read from a snapshot older than **Maximum
Debt Age (hours)** (default 24, set by managers) is refused with a
generic "out of date" error, in the agent's ``customer_debt``, in the
Add Debt picker and when an allocation snapshots its lines, instead of
serving stale figures. Every debt answer carries ``as_of``: the
snapshot's refresh time, or the read time when a profile reads debt
live, shown in the company timezone.

Debt list: **Collections > Bejerman Debt** (Collections Managers only)
lists every open invoice, quotation and credit note of the snapshot,
read-only, with amount and balance totals. Credit notes (kind **Credit
Note**) carry their negative balance, so the balance total nets them;
they are listed only and never offered as debt to allocate. It searches
by customer name or code, seller code and number, filters invoices,
quotations, credit notes and overdue rows, and groups by customer code,
seller code and kind. The customer name is read from the customer
snapshot of the same refresh, not stored.

Sheets entered in the ERP: receipts are typed into Bejerman by hand and
a collections manager marks the closed sheet **Entered in the ERP**
(``collection``). Its applied amounts keep being subtracted from the
Bejerman balances until a refresh that **started** after the mark
succeeded (the snapshot then shows the entry); a refresh that started
earlier, even if it finished later, releases nothing. A profile that
reads debt live answers at question time, so marked sheets are no longer
subtracted.

Customer debt reads the snapshot: ``state`` is ``overdue`` when the due
date is before today in the company timezone, else ``open``, computed at
read time. Credit notes (decision D4): the invoice list is unchanged and
allocations still target invoices, but the answer carries the customer's
open ``credit_total``, so the ``collection`` summary reports
``gross_total`` (open invoices), ``credit_total`` and ``net_total``
(what the customer owes, also ``total_balance``): a 1000 invoice and a
300 credit note give 700. Test Connection probes Registro and
``ObtenerClientes``, then Cierre; the debt views are exercised by the
refresh.

Sellers: Bejerman has no seller view, so the profile reads the sellers
along with the debt, and ``list_sellers`` reads the seller snapshot and
makes no Bejerman call (before the first refresh it fails closed like
the customer reads). Bejerman supplies only the code and name; Odoo
keeps the rest and ``list_sellers`` merges it back so an import never
overwrites the administrator's values: commission is the seller
binding's ``commission_percent``, the phone is the bound user's partner
phone, and ``active`` means the bound user is in the company's enabled
sellers. A seller without a binding is listed inactive, commission 0, no
phone. The generic ``collection`` list drops inactive rows, so only
bound and enabled sellers reach the import. On the connector form, the
commission of a seller binding is editable only for Bejerman connectors
(collections managers and administrators already hold write access on
the binding); the next import keeps it.

Enabling a seller: because the generic import only lists sellers that
are already bound and enabled, a new seller is enabled from the
connector form, **Sellers** tab (the seller snapshot with its Odoo user,
commission and enabled state). The row button **Enable seller** opens a
wizard: pick an internal user that already belongs to the company
(checked on the server too, so enabling never widens a user's company
access) or create one (login ``collection.<company id>.<code>``, name
prefilled from Bejerman), then set the phone and commission. Confirming
creates or updates the binding, writes a changed phone on the user's
partner as the current user (never with elevated rights; if the manager
may not edit that contact, an error asks an administrator to set it and
nothing is written), and adds the user to the company's enabled sellers,
with no Bejerman call and no import. A user already bound to another
code, or a phone used by another enabled seller, is refused. **Disable
seller** removes the user from the enabled sellers and keeps the
binding. Administrators and collections managers only, Bejerman
connectors only.
